# Ordinary Desktop Remote Input v1

`P0-DS-09` adds explicitly authorized keyboard and mouse control to the ordinary logged-in Windows desktop. It reuses the reliable ordered `redclaw-control-v1` DataChannel and does not create another transport channel.

This version does not cross Windows integrity or desktop boundaries. Administrator/elevated windows remain subject to UIPI, and UAC, the sign-in screen, the secure desktop, Ctrl+Alt+Del, game-style relative mouse input, clipboard, and mobile input are outside this contract.

## Authorization and states

The Host connection page owns the local authorization decision. `QSettings("RedClaw", "RedClawDesktop")` stores `host/allow_remote_control` for the current Windows user; the first-run value is `false`. Entering Host wait snapshots the checkbox into the runtime launch as `--allow-remote-input`, locks the checkbox, and shows either remote control allowed or view only. Automatic reconnection keeps that wait-cycle authorization. Manual stop or process exit destroys the runtime grant without deleting the stored preference.

Runtime profiles accept `allow_remote_input=true|false`; the default remains false for CLI, automation, Debug, and Release. Authorization belongs only to the current runtime connection and control epoch. It is not bound to a Controller fingerprint in v1.

Host reports one of `unavailable`, `available`, `active`, `paused`, or `denied`, with typed reasons including unsupported, not authorized, no video, local pause, lease expiry, queue overflow, injection failure, disconnect, geometry change, and stale sequence. Missing input capability messages are interpreted as view-only compatibility.

## Protocol messages

Every input message uses the normal control envelope: schema version, session epoch, increasing message ID, and timestamp. The input extension adds:

| Message | Direction | Purpose |
|---|---|---|
| `input_capabilities` | Host to Controller | Support, authorization, state, capture origin/size/rotation/revision |
| `input_control_request` | Controller to Host | Explicit start or stop request |
| `input_control_status` | Host to Controller | State/reason and last applied input sequence acknowledgement |
| `input_batch` | Controller to Host | Up to 64 typed events and at most 4 KiB |
| `input_state_sync` | Controller to Host | Pressed scan codes/button mask every 500 ms |
| `input_release_all` | Controller to Host | Immediate fail-closed release and pause |

`RemoteInputEventV1` carries a scan code, virtual key, extended and repeat flags, normalized coordinates, mouse button, and vertical or horizontal wheel delta. Validation rejects zero/out-of-range scan codes, inconsistent per-event fields, invalid buttons/wheels, more than 64 events, oversized batches, stale epoch/message IDs, and non-increasing input sequences. The protocol and diagnostics never log individual key values or text.

## Controller capture

The Controller button requests Host activation first. An `active` status enables the user's control intent and installs the Windows `WH_KEYBOARD_LL` hook. Control intent and current forwarding eligibility are separate: `control_enabled` remains true until explicit Stop, the emergency shortcut, disconnect/epoch change, authorization loss, lease/queue/ACK failure, injection failure, or control-channel failure; `input_forwarding` is true only while the playback window is visible, restored, foreground, and outside a geometry transaction. The playback window titled `RedClaw` is an independent top-level window, not a Windows owned window of `RedClaw Desktop`. Minimizing or activating the main window does not hide or raise it. Closing the playback window returns to the main window and does not quit the process. Forwarding follows the playback window's own state. Window deactivation, hide/minimize, and geometry changes combine as `window_inactive`, `hidden_or_minimized`, and `geometry_transaction` suspension flags. Clearing every flag automatically resumes forwarding without another Host request.

Every non-injected hook event rechecks the playback foreground-window identity. While locally suspended it is passed through to Windows and never queued remotely. The hook preserves scan code and extended-key identity, marks genuine auto-repeat, and suppresses captured keys locally so Alt+Tab and Windows keys reach the Host only while forwarding is enabled. Host keyboard layout and IME interpret the physical-key stream; local Unicode/IME commits are not transported.

Shift scan codes `0x2A` (left) and `0x36` (right) are normalized to non-extended before Controller pressed-key tracking and serialization. The Windows low-level hook can flag right Shift as extended, but `KEYEVENTF_EXTENDEDKEY` injection denotes an E0-prefixed scan code, which neither Shift uses. Host applies the same normalization to keyboard batches and pressed-state snapshots from existing Controllers, so a Host update alone corrects their right Shift input. Down, repeat, up, state reconciliation and cleanup use the same physical identity; right Ctrl/Alt and other genuine extended keys retain their flag. The v1 wire schema is unchanged.

`Ctrl+Alt+Shift+Esc` is a Controller-local emergency exit and is never sent. Ctrl+Alt+Del is suppressed from the remote protocol because ordinary `SendInput` cannot implement it. RedClaw does not take an explicit process-wide mouse grab, so the Stop Control button and the rest of the local UI remain directly usable.

Mouse coordinates are calculated against the latest successfully displayed frame's aspect-fit content rectangle. Movement, button-down, double-click, and wheel events outside that rectangle, including letterbox bars and other Controller UI, are never sent and do not alter control intent. A drag that began inside may deliver its matching ButtonUp after the pointer leaves only as state cleanup: it uses the last valid in-content coordinate and does not move the Host pointer. This exception prevents a stuck remote button without turning outside-window activity into remote input. On Windows, spontaneous candidate Qt mouse events read the current message's [`GetMessageExtraInfo`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessageextrainfo) value before queuing; movement, button, double-click, release, and wheel events carrying RedClaw's shared `SendInput` marker are consumed locally. Physical events and other marker values continue normally. This breaks same-session Host-to-Controller mouse feedback without adding a global mouse hook.

Entering a local suspension clears unsent events and locally tracked keys/buttons, immediately sends an empty `input_state_sync`, and continues empty syncs every 500 ms. Host releases its tracked input but remains `active`, so the three-second lease does not expire during a long minimize or focus loss. `input_release_all` is reserved for a real terminal transition. Reconnect never automatically restores Controller control intent.

Desktop navigation retains the previous control intent when changing displays or capture regions. The input owner waits for both the matching Host region acknowledgement and a successfully presented frame before clearing `capture_region_change`; window resize, local panel focus and other suspension reasons remain independent. Rejection returns to the confirmed target without enabling a previously view-only Controller, and late completion cannot undo Stop. A requested display restart rejects old capture generations and keeps only empty lease syncs and explicit Stop messages until the new frame is presented. Geometry resets are consumed by the Host runtime loop, release held input and discard queued events without renewing consent. Normal navigation never requires another Start Control request; actual capture failure, authorization loss, disconnect and lease expiry still end control. That control-continuity repair kept the wire schema unchanged; the optional command capability below extends it separately. Both Controller navigation handling and Host capture/input handling require the continuity repair for this behavior; older peers continue to connect normally and retain their existing navigation behavior.

When control is disabled, a mouse press on the playback canvas is consumed locally. One mouse-transparent, focus-free overlay displays a red prohibition symbol for two seconds, with either “未开始控制，请点击 Start Control” or the view-only reason. Repeated presses only restart the same timer. The overlay is an independent frameless surface, so D3D11/OpenGL/Qt canvas geometry and swap-chain resize counts do not change. `blocked_control_click_hint_total` records only the count.

## Navigation command capability

The Host advertises optional `capture_region_command_version=1` in its display catalog.
An updated Controller echoes version 1 and sends `capture_region_request_id` for
correlation; it does not propose a capture revision. The Host executes valid commands
and assigns the next capture revision on its capture worker. Applied/rejected replies
echo the request ID. Applied replies and video frames carry the Host-owned revision.
The input owner matches the request ID, then waits for presentation of that revision
before releasing navigation suspension. Old replies cannot finish a newer request.

An absent capability selects the published legacy contract: requests supply a revision
above the observed Host revision, and replies echo it. New Hosts continue accepting
that contract for old Controllers. Optional fields are ignored by old readers;
unsupported command semantics report `protocol_version_incompatible`. Authorization,
focus, capture availability and lease checks are unchanged. Reconnect clears pending
navigation and renegotiates from the next catalog; it never blindly replays a command
from the previous peer session. A Host retaining the session retains its capture region.

## Host mapping and injection

Capture frames advertise the source desktop origin, dimensions, rotation, and geometry revision. Controller coordinates use `0..65535`. Host maps them to the current capture rectangle, including negative virtual-desktop coordinates and 0/90/180/270-degree rotation, before the Windows backend converts the physical point to `SendInput` virtual-desktop absolute coordinates.

Keyboard injection uses `KEYEVENTF_SCANCODE` and `KEYEVENTF_EXTENDEDKEY`; mouse injection uses batched `SendInput`, `MOUSEEVENTF_ABSOLUTE`, and `MOUSEEVENTF_VIRTUALDESK`, including X1/X2 and both wheel axes. Capture geometry is in physical pixels. For the duration of each injection batch the injector thread uses per-monitor DPI awareness v2, so the virtual-screen metrics match that physical desktop, and then restores the thread's previous context. The rest of the process stays DPI-unaware. Normalized Controller coordinates and the wire protocol are unchanged; a Host update is sufficient. Every injected event carries the public `redclaw::input::kRedClawInputExtraInfo` marker in [`dwExtraInfo`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput), so the keyboard hook and Controller mouse guard can identify feedback from the same RedClaw injection contract. A partial `SendInput` result triggers compensating key/button releases and fail-closed pause.

Network callbacks only validate and enqueue. The runtime loop owns the input session and processes it before heartbeat, viewport/statistics, and remote-log output. Critical Controller events use a 256-entry FIFO; mouse move is latest-only and flushed at no more than about 60 Hz. Host has a 256-event queue. Overflow, invalid mapping, injection failure, or a control-channel backlog at or above 64 KiB pauses input instead of dropping KeyUp/ButtonUp silently. Remote log chunks are withheld while input work is pending.

The Controller sends a full pressed-state sync every 500 ms. Host only uses it to release locally tracked states that the Controller no longer reports; it never invents a press from a sync message. A three-second lease releases all tracked keys/buttons and pauses the session. Disconnect resets the input sequence for the next epoch.

Debug QA uses the same lifecycle instead of a second injection path. The current-user local control pipe can request Start/Stop Control, one normalized paired mouse click, or one paired scan-code key press. Start still requires Host authorization, open control channel, and a real displayed frame; key QA additionally requires current forwarding eligibility. Queue/ACK pressure, denial, disconnect, or send failure ends control and releases all input, while local window suspension only emits empty state sync. Responses expose `control_enabled`, `input_forwarding`, combined suspension reasons, the blocked-click count, queue/counter deltas, loopback suppression, and acknowledgement RTT; neither side logs the requested key value or text. Host runtime logs then provide count-only confirmation that a batch or empty sync was applied.

## Telemetry and validation boundary

Host heartbeat telemetry records received/rejected batches, injected event count, release-all count, queue peak/current depth, last applied sequence, and capabilities/status totals. Controller status logs are rate-limited and record sent batches, coalesced moves, suppressed same-session mouse-loopback events, blocked-click hints, acknowledgement RTT, and a bounded rolling P95 without recording key content. Debug `tail_log` reads the already-redacted 4096-line/1 MiB `ProcessFileLogger` memory ring rather than scanning `QPlainTextEdit`; it returns at most 200 lines with a 64 KiB snapshot limit and a 48 KiB JSON log-array budget, plus elapsed/truncated fields. There is no unbounded GUI-text fallback.

Validation covers protocol, runtime-profile, input-session, connection-flow/UI, and bounded-log behavior plus standard Debug and Release builds. Local dual-GUI acceptance must prove real capture, encoded transport, hardware presentation, authorized input, minimized-window suspension, forwarding recovery, explicit Stop, and bounded diagnostic export. Physical two-machine input, forced disconnect, and measured LAN acknowledgement latency remain separate acceptance evidence; elevated and UAC targets require their dedicated runbook.

## Opt-in cross-machine delivery evidence

Launch each Debug GUI with `--input-diagnostics --enable-debug-control --stream-smoke` and a log directory (the cross-LAN launcher exposes `-InputDiagnostics`). This does not enable the synthetic Agent fixture, generate input, authorize remote control, change privileges, or alter the wire protocol. The normal Host consent and Controller Start Control gates remain required. Release rejects the option.

On the Host, the owner-local `input_probe_start` command opens a passive ordinary-desktop target window. Click that target through the Controller playback window, then use a small bounded set of normal keys and clicks. The target counts only messages addressed to its own HWND, separates RedClaw-marked native messages from other input, and counts Qt-delivered events without retaining key values or text. It adds no global hook. `input_probe_stop` stops target recording; it does not stop remote control.

After the measurement, invoke `input_probe_export` separately on both machines. Runtime output is asynchronous: verify the matching `input-injections-<generation>.json` manifest before using its referenced `input-stages-<generation>.json`. The Host also writes `input-target-<generation>.json`. Host export pauses input using the existing local release path; Controller export does not send a remote pause. Begin another runtime recording interval with a fresh Start Control request. Overflows invalidate claims of complete event coverage.

The existing v1 evidence files gain optional fields; old fields and stage IDs remain unchanged. Category arrays use key-down, key-up, move, button-down, button-up, wheel, horizontal-wheel order. Stage records carry the input sequence and counts; appended stages 27–30 mean geometry rejected, mapping rejected, session rejected, and session enqueued. Injection receipts correlate sequence/type with the native call interval. Native calls record requested/inserted counts and immediate error; at most once per 250 ms they also sample the actual injector thread's session/desktop, foreground/focus PID, integrity levels, and cursor position. Desktop kinds are 0 unknown, 1 Default, 2 Winlogon, 3 other; missing context is explicit. Absolute timestamps must only be compared within the same machine's monotonic clock domain. Target receipts do not claim a wire sequence mapping.

Interpret the chain in order: Controller category generation → Host parse/queue/mapping → session enqueue → native insertion → target native message → target Qt event. Aggregate sent/received counts and empty state-sync acknowledgments alone cannot prove that a particular key or click traversed the chain. [`SendInput`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) returning the full requested count proves insertion, not application consumption; its error code cannot uniquely identify UIPI. A sampled Default desktop does not prove there was no earlier UAC interval. These diagnostics never bypass secure-desktop or authorization gates.

## Explicit local native-window experiment

`redclaw_native_input_window_probe` is an optional Windows developer target, excluded from the default build and never registered with CTest. Build it with `./build.ps1 -Configuration Debug -Target redclaw_native_input_window_probe -NoPublish`. Run its Debug executable interactively with `--output <new-local-jsonl-file>`; when using `Start-Process`, select `-WindowStyle Normal` so the owned test window can become visible and focused. Do not run it during unrelated desktop interaction.

The baseline uses the production Windows injection backend to send one mouse move, one paired left click and one paired digit 7 to its own harmless window. Visibility/hit-test, foreground and held-input checks gate injection. Actual marked native mouse/key messages and the owned window's character receipt are recorded separately: `WM_CHAR` may lose the injection marker during translation. No process token or desktop identity is queried. The tool closes its window and requests restoration of the previous foreground only if its own window still owns foreground.

Use `--start-signal <absent-local-file>` when the operator first needs to confirm visibility. The window is placed on the previous foreground window's monitor and displays a passive waiting state for at most five minutes. It sends no input before the caller creates that file after confirmation; an expired or closed preparation cannot pass the baseline. Window enumeration or an offscreen rendering receipt alone does not replace the operator's visibility confirmation.

For asynchronous operator handoff, use `--manual-start` instead. It displays a visible **Start local test** button and waits up to 30 minutes without sending input. Clicking the button confirms visibility and starts the released-input/stable-focus gate locally; chat response latency cannot start or expire an already-running observation before the operator is ready. Closing the window cancels it. This option cannot be combined with `--start-signal`; the actual observation remains separately bounded by `--observe-seconds`.

With explicit user authorization, `--observe-seconds N` adds a bounded observation interval (maximum 300 seconds) after the baseline. Every five seconds it attempts movement to a visible point inside its own window, skipping occluded targets or held input; it sends no additional clicks or keys. An optional machine-local `--watched-process-file` contains selected process IDs only for foreground classification, while output exposes only `probe`, `watched_product` or `other`. Keep the probe unobscured while the operator activates the comparison window. Closing the probe ends observation.

The separately selected `--recover-on-delivery-gap` experiment requires both observation and a watched-owner file. Its owned target temporarily stays topmost without activation to avoid occlusion. Three consecutive samples must retain the same watched foreground, pass the target/held-input gates, have a cursor restriction rectangle that includes the target, and report API insertion success with neither native target movement nor arrival at the point. Only then does the same process create a second ordinary window and request foreground activation once. There is no injected activation shortcut, foreground-lock setting change, thread-input attachment or privilege change.

Successful activation is checked independently of the API return. Only after it is verified does the unchanged backend send movement and a paired click to the original target, followed by one paired digit 7 once that original target has focus. Native down/up and character deltas must all be present. A new process or target-only success cannot satisfy this same-instance recovery experiment. Recovery mode returns exit 4 when no qualifying gap is observed or recovery fails; its result distinguishes these cases. Both owned windows are cleaned up. This diagnostic experiment does not itself implement production automatic recovery.

This experiment verifies local backend insertion versus native target consumption. It does not exercise Controller hooks, transport, remote capture mapping, another operating-system/product version, or historical failure state. A passing ordinary-window baseline is not a passing third-party-window reproduction test. Preserve skipped/gated samples and failed instrumentation attempts separately from product failures.

## Bounded ordinary-window recovery

Latest acceptance clarification (2026-10-18): the operator authorizes retaining the existing foreground-changing popup and removing the old retry delay after observed recovery, while keeping backoff for unsuccessful recovery. This replaces the earlier foreground-preserving-only requirement; it is not evidence that instantaneous or universal filtering detection is available. The goal remains restored control of ordinary applications, not access to the security application's UI. The deployed fast-rearm candidate passes operator-assisted recurrence and ordinary-window-click acceptance; see the [module kanban](../runtime/MODULE_KANBAN.md#m05-input). Foreground activation and cursor progress alone do not establish ordinary-application consumption.

The Host input runtime wraps its ordinary injector in `RecoveringInputInjectorBackend`. It observes only real, authorized absolute mouse movements; it does not generate probe input, repeat an old click/key, or change the wire protocol. One pending observation is allowed, sampled at most once per 250 ms and checked at least 200 ms later through the existing runtime loop. There is no additional worker, timer wakeup, blocking wait or disk write on the normal input path.

Three consecutive samples must report native insertion success with a stationary cursor despite a target more than 16 physical pixels away. They must retain the same foreground and point window, an unclipped target on a real monitor, released mouse/modifier state, and the injector's ordinary visible input desktop. Cursor progress, mixed/key/button input, stale samples, foreground/target changes, capture or authorization epoch changes discard the observation. Session consent, active control, live capture, lifecycle channel, transfer state, lease and remotely held keys/buttons also gate recovery. This is a conservative symptom detector, not proof of a third-party filtering mechanism or target consumption; keyboard-only stalls and cursor-moving delivery failures are outside its scope.

On a qualifying stall, the platform rechecks the desktop and all held keys and makes one normal request to activate a small owned window. Windows may deny this request. No synthetic activation shortcut, input-thread attachment, permission/configuration change or desktop switch is used. The window requests that the user move the mouse and click another application. It remains while it owns foreground, because a timed close can reactivate the same blocking application; it closes on foreground loss, explicit user close or revocation of its authorization/capture/lifecycle/transfer context. It does not restore or reactivate the previous foreground. Held input blocks observation and new activation, but does not destroy the existing window between ButtonDown and ButtonUp. At most three attempts are allowed without observed cursor progress, separated by at least 30 seconds and still requiring fresh real movement and three qualifying stationary observations. No timer-only retry occurs. Later validated cursor progress resets both that budget and the failure cooldown, including a coalesced move beyond the original point. A fresh failure must still pass the complete detector before another activation. Logs distinguish attempts from verified foreground activation and explicitly leave application delivery unverified.

Real cursor progress is also observed while the owned recovery window has foreground, so it can clear the previous failure's cooldown and re-arm a later recurrence. A stationary owned window never triggers recursive activation. The existing ten-second telemetry cadence additionally distinguishes gated, stale, changed-target, held-input and mixed-input observations, retry-budget/cooldown suppression, and owned-window closure by user, foreground loss or context/desktop loss. Window lifetime is recorded without window identity. Closing the window, changing foreground or toggling the control context alone does not establish progress or clear the failure backoff/budget. This mitigation does not make a blocking application accept input: deliberately returning to that foreground can reproduce the stall.

The native recovery window follows the GUI shell's dark navy palette, light text and blue emphasis, with a rounded message panel and DPI-scaled text/client size. It retains the native caption and close action. Its operator-requested message is “当前激活窗口禁止键盘鼠标消息注入，请关闭此软件窗口。”; the close instruction is emphasized, followed by guidance to move the mouse and switch windows. This presentation does not change the detector or establish the underlying filtering mechanism. Painting remains local to the owned window, without a Qt dependency, extra input, replay, worker or timer; unsupported Windows title-bar color attributes keep the normal native frame.

The manual probe's `--automatic-recovery` mode exercises this production adapter instead of the separately triggered experimental activation; it cannot be combined with `--recover-on-delivery-gap`. Its one-second movement interval remains bounded by `--observe-seconds`. Original-target mouse/key/character receipts are checked after an owned recovery window actually gains foreground. Production activation counters alone never qualify that result.

### Detection latency and coverage

There is no direct downstream-filter receipt in the current `SendInput` path. Its insertion count can report an immediate API failure, but cannot establish the filter's identity or that later hooks/the destination accepted an otherwise successful insertion. Current recovery deliberately detects a symptom using subsequent actual cursor position, not a third-party block notification.

With continuous qualifying movement, a ready observer and no cooldown, the 250 ms sampling interval, 200 ms settling interval and three required gaps give a nominal earliest decision of about 700 ms from the first qualifying sample (samples at 0/250/500 ms, final observation at 700 ms). Runtime/input scheduling adds delay; approximately 0.7–1 second is a parameter-derived ideal-case estimate, not a measured end-to-end bound. No upper bound is guaranteed when movement stops, clicks/keys interrupt the streak, target/foreground changes, a safety gate closes or the runtime stalls.

Every activation attempt starts a 30-second failure cooldown. Before the fast-rearm change, cursor progress reset the attempt budget but retained this cooldown, delaying a new failure after recovery. The fast-rearm implementation clears both only after an authorized movement observation reports cursor progress with unchanged foreground/target and valid context; all existing gates and the three-gap threshold remain. Keyboard-only loss and mouse-button rejection with a moving cursor are outside the detector's coverage. This is a cursor-recovery signal, not proof of application consumption or which physical/software source moved the shared cursor.

The deterministic regression comparison uses identical injected-event and observation timings: the old implementation suppresses the first recurrence at 3000 ms; the fixed implementation activates at 1800/3000/4200 ms for the initial failure and two recovered-then-failed episodes. Both recurrences take 700 ms from their first qualifying sample (2300/3500 ms), with no replay or extra input. Two regressions fail on the old implementation; all 16 recovery cases pass after the change, including unsuccessful activation/backoff, bounded retries, context/held-input gates and popup lifetime. These are simulated-clock state-machine results, not peer wall-clock measurements or Tencent compatibility acceptance. Evidence: `input-recovery-fast-rearm-20261017-01`.

## Background recovery assessment and upstream evidence (2026-10-17)

The reproduced Tencent PC Manager foreground dependency supports an external input-filtering hypothesis; it does not identify a hook, driver, UIPI failure, or behavior of all Tencent applications. The later operator report below also prevents treating foreground ownership alone as a sufficient failure condition. Ordinary window procedures do not forward the entire desktop input stream. A low-level hook can suppress delivery to later hooks and the target procedure, as documented by [Microsoft](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc). This is a possible mechanism, not an observation of PC Manager's internals.

Source inspection finds a per-batch `SendInput` call with freshly constructed `INPUT` records. `WindowsSendInputInjectorBackend` owns only an optional observer and diagnostic sampling timestamp, not a native injection handle or worker that can be reset. The recovery adapter observes symptoms and activates an owned window; it does not repair the underlying injection path. [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) reports insertion, not target consumption. [BlockInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-blockinput) only permits the blocking thread to unblock; no blanket `BlockInput(FALSE)` recovery is justified. Attaching input threads, changing input markers, replaying events, or reconstructing the backend has no demonstrated remedy here.

The upstream comparison distinguishes confirmed implementations from reports:

- [RustDesk discussion 13793](https://github.com/rustdesk/rustdesk/discussions/13793) closely matches the symptom: video continues, Avast foreground loses keyboard/mouse control, another foreground restores it, and reactivation loses it again. The reporter already uses a service and reports other elevated applications working. Replies describe disabling Avast input-manipulation protection and differing results between builds; these are environment-specific user workarounds, not a merged background-recovery fix. [Issue 6336](https://github.com/rustdesk/rustdesk/issues/6336) similarly contains build-dependent reports and an unreproduced diagnosis, not proof that a closed issue was fixed. RustDesk's inspected [Windows Enigo backend](https://github.com/rustdesk/rustdesk/blob/master/libs/enigo/src/win/win_impl.rs) also calls `SendInput` for mouse and keyboard.
- [MeshCentral issue 633](https://github.com/Ylianst/MeshCentral/issues/633) reports working video and terminal with input blocked by Avast UI. Its [final reply](https://github.com/Ylianst/MeshCentral/issues/633#issuecomment-2503697681) attributes this to Avast's security feature and says it will not be fixed. Earlier exclusion-list and foreground-switch suggestions are not portable input-recovery mechanisms.
- [UltraVNC issue 73](https://github.com/ultravnc/UltraVNC/issues/73#issuecomment-1438941035) is a distinct UIPI case: the maintainer explains the integrity-level restriction, and the reporter confirms administrator execution solved it. RedClaw has not established that cause here; this does not authorize elevation or security-setting changes.
- Sunshine has merged [libvirtualhid integration 5368](https://github.com/LizardByte/Sunshine/pull/5368) and [Raw Input mouse support follow-up 5547](https://github.com/LizardByte/Sunshine/pull/5547). Its [Windows documentation](https://github.com/LizardByte/Sunshine/blob/master/docs/getting_started.md) describes driver-backed normal keys, relative movement, buttons and scrolling, while Unicode text and absolute mouse positioning retain Windows injection. The [library documentation](https://github.com/LizardByte/libvirtualhid) distinguishes its MIT library from the separately licensed Windows driver/broker. This is a concrete alternative input architecture with installation, licensing and validation costs; neither its Raw Input fix nor its merge proves Tencent compatibility or a drop-in fix for RedClaw's absolute pointer path.

The background-only investigation established no reset that preserves foreground, existing authority and security configuration while restoring delivery. Its earlier foreground-preserving acceptance has since been revisited by the operator's conditional acceptance of prompt detection plus popup recovery above. Keep M05-T03 open. Ordinary-application consumption remains necessary, without requiring consumption inside the protected application. Signing/vendor trust, UIPI handling and virtual HID remain separate hypotheses or engineering scopes, not automatic fallbacks. Do not generate more target input merely to reconfirm the existing foreground correlation.

### Recovery-window transition distinction

The operator clarifies that “remote control again” meant the existing recovery prompt appearing, not disconnect/reconnect or a process restart. After that prompt, clicking PC Manager's real-time-status window permits operation; clicking another window and then returning to real-time status loses control again. A later report specifically confirms mouse movement after several clicks in that window. These are operator observations, not yet a timestamp-aligned foreground/target-consumption trace. Cursor movement alone does not establish that PC Manager accepted the clicks or became the actual foreground window.

The meaningful comparison is therefore recovery-prompt-to-target versus ordinary-window-to-target. In the current implementation, the first path additionally destroys the owned recovery window after `pump_window` observes that it has lost foreground. Creation, showing, activation, message processing and destruction occur within the same recovery flow; the observations do not isolate which action or ordering matters. There is no reconnect or backend reconstruction in that flow. Do not infer that a session reset, a standalone message pump, or creating/destroying an inactive window would recover delivery.

Static lifecycle inspection remains useful but is not a remedy: Controller pause/activate reinstalls its local keyboard hook and clears local pending/held state; Host `request_active` releases its tracked input, clears its queue and renews the lease; disconnected pause additionally clears the received sequence. Held-state deduplication applies to keys/buttons, not absolute mouse movement. These mechanisms do not by themselves explain the earlier accepted movement batches with a stationary Host cursor, and this operator report is not evidence that reconnecting repairs them.

The completed 60-second passive observation (`input-activation-sequence-20261017-01`) records 1046 samples, a maximum 72 ms gap, no GUI-state query errors and no dropped transition records. The recovery prompt initially owns foreground; 216 cursor-position changes accumulate before its foreground loss at 22.762 seconds, with its disappearance observed at 22.816 seconds. The count stays 216 until a second recovery prompt owns foreground at 25.750 seconds, reaches 229 by its foreground loss/disappearance at 27.330 seconds, then stays 229 to the end. All sampled GUI flags are zero and foreground-thread mouse capture is absent. These snapshots do not rule out short-lived states or identify a hook/driver. Other foreground identities are temporary aliases, not classified PC Manager windows. No input, activation, hook, process restart or system change is generated by the observer, and the terminal returns to its ready prompt.

The operator then clarifies that the cursor can move but buttons inside real-time status do not respond.
