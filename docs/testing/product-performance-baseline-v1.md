# RedClaw 产品性能基线 v1

**生效日期：** 2026-09-11
**状态：** 基线定义已采纳；严格性能门禁已退出功能开发阻塞链
**适用任务：** P1-AG-01R 的 GUI、输入、Agent 输出与桌面呈现并发性能

## 1. 决策

从本版本起，将开发和发布决策分为四类：

1. **正确性硬门禁**：任何构建和负载都不得丢文本、丢控制消息、破坏输入授权/
   租约、静默溢出或产生解码/呈现失败。
2. **功能开发继续门禁 `DEV-FUNC-1`**：只检查真实路径身份和功能正确性。性能数值
   不参与通过判定，避免硬件与极端 Debug 负载阻塞未完成的产品功能。
3. **产品性能基准 `PB-REL-1`**：使用与 Release 相同优化级别的 QA 包和有节奏的
   代表性负载，供发布候选决策使用；在功能开发阶段只报告，不阻塞主线。
4. **研发隔离压力 `DBG-X1`**：保留现有 Debug 双向无节奏 1 MiB 长行测试，用于暴露
   热路径阻塞和比较回归。其正确性失败仍然阻断；100 ms、250 ms、90% 三项性能值
   继续报告并跟踪，数值失败本身不阻塞功能开发或代表产品 Release 性能。

历史有效失败不改写。既有 Debug 压力运行的输入、心跳和 FPS 在 `DBG-X1` 下仍为
失败；同一轮运行已通过 `DEV-FUNC-1` 的功能正确性检查。
因此 P1-AG-01R 不再因本机性能阻塞功能主线。在 `PB-REL-1` 可运行并取得完整证据
前，发布性能状态为 **unverified**。

### 1.1 功能优先的阶段策略

`DEV-FUNC-1` 只用于当前产品功能尚未完备的开发阶段。它不是用户体验承诺，也不能
替代发布前的 `PB-REL-1`。判定使用固定 Debug 产物的一轮有效 public-DHT、真实采集、
真实编解码和原生 D3D11 证据；具体产物身份只保存在被 Git 忽略的本地报告中。

- 文本、诊断、三通道、输入租约和零解码/呈现失败等正确性门禁全部通过；这些要求
  不因硬件较弱而放宽。原生 D3D11 surface 归入硬件能力观测，不阻塞功能开发。
- 真实路径和产物身份必须可核对。正确性与身份决定 `passed`；输入、ACK、心跳和 FPS
  不参与功能继续判定。
- 当前研发机仍以输入 P95 `150 ms`、ACK `<250 ms`、心跳 `<500 ms`、绝对
  `12 FPS` 和配对 `75%` 作为 `PERF-OBS-1` 非阻塞报警线。越线进入性能待办，不能
  改写功能完成状态。
- 一轮完整有效证据用于建立当前校准观测；三轮和参考硬件资格属于发布候选阶段。
  任何正确性失败仍立即阻断。

`scripts/service/evaluate-development-readiness.ps1` 生成 `DEV-FUNC-1` 和
`PERF-OBS-1` 的独立结论。实际延迟、心跳、FPS、产物哈希和硬件身份写入被 Git 忽略的
本地报告，不作为公开源码树中的固定事实。

## 2. 参考环境

`PB-REL-1` 是性能资格环境，不是最低支持配置声明。

| 项目 | 固定条件 |
| --- | --- |
| 操作系统 | Windows 10 22H2 或受支持的 Windows 11；记录版本与 build |
| CPU | x64，至少 4 个物理核 / 8 个逻辑线程 |
| 内存 | 至少 16 GiB；测试开始前至少 4 GiB 可用 |
| Host 图形路径 | D3D11 可用；H.264 硬件编码成功，记录 GPU、驱动和实际 backend |
| Controller 图形路径 | D3D11 hardware surface 解码与 Video Processor 呈现；不得依靠 CPU transfer、software frame 或 surface fallback |
| 桌面 | 1920×1080、60 Hz、100% 或 125% DPI；原生可见尺寸必须写入报告 |
| 供电/后台 | 接通交流电；记录电源模式；采集前 60 秒平均后台 CPU 小于 10%，否则窗口无效 |
| 构建 | `NDEBUG` 和优化选项与 Release 相同的 `Release-QA`；不得附加调试器 |
| 拓扑 | 同一参考机运行独立 Host/Controller GUI 和 runtime，通过 public-DHT 建立真实 ICE/DataChannel；两端包 SHA256 必须相同 |

不满足上述固定环境、硬件清单或显示条件的机器只能用于研发校准和兼容性测试，
不能据此降低 `PB-REL-1` 基线。

`Release-QA` 仅允许加入确定性 fixture 和本地证据控制；编译优化、Qt、编解码、
网络、输入和呈现代码必须与 Release 相同。QA 入口不得写入用户设置，也不得出现在
正式发布包中。实现时必须输出产品 Release 与 Release-QA 的编译选项差异清单。

## 3. 产品负载 `AGENT-PACED-1`

当前真实 Provider 没有稳定、可复现的输出语料和节奏，因此 v1 采用明确的上界型
代表性 fixture，后续用真实 Provider 遥测校准，而不是用无节奏 1 MiB 代替产品负载。

- Host 和 Controller 各启动一个独立任务，开始时间相差不超过 500 ms。
- 每端输出 120 个 UTF-8 chunk，每个 1024 字节、间隔 250 ms，总计 120 KiB，
  持续 30 秒。Provider 必须保留 120 个源事件和各自时间；GUI 可使用现有有界合批，
  但不能因此丢失文本、源计数或窗口边界。
- 确定性语料按字节包含：70% 普通说明文本、25% 代码/日志、5% 1–4 KiB 长行；
  含换行、空格和 Markdown。生成器 seed、语料 SHA256、最终文本 SHA256 写入报告。
- 最后一块后立即产生 terminal 事件。任务运行期间不执行命令，不访问外部 Provider。
- 默认主门禁保持 Agent 面板可见、跟随终态；另做一次隐藏后恢复、一次滚动和一次
  窗口缩放的正确性覆盖，不能用隐藏面板代替可见终态绘制。
- 桌面动态场景稳定在 `30 ± 2 FPS`。场景低于 28 FPS、焦点/几何变化、租约变化或
  trace 容量不足时，该窗口标为 invalid 并完整重测。

每轮固定为：空闲 30 秒 → `AGENT-PACED-1` 压力 30 秒 → 两端 terminal 已可见后恢复
30 秒。每种产品配置连续三轮；不能缩短窗口或删除有效慢样本。

## 4. 产品 KPI 与发布基准

### 4.1 主要 KPI

| KPI | 精确定义 | `PB-REL-1` 门槛 | 决策用途 |
| --- | --- | --- | --- |
| 输入接收延迟 | Controller 实际发送至 Host 测试目标原生分发；同一序列 down/up 取较慢值作为一个批次 | 每轮 idle/pressure 的键盘、鼠标各 ≥100 个独立批次，P95 `≤100 ms` | 产品交互响应 |
| 成功新帧 FPS | 只计成功提交的新帧；旧帧重绘、忙丢帧不计 | 每轮 pressure 和 recovery 均 ≥该轮 idle 的 90%，且三个窗口绝对值均 `≥15 FPS` | 视频连续性；绝对下限防止低基线假通过 |
| GUI 运行心跳 | 事件循环开始后相邻心跳间隔；启动构造不混入 | 两端每个有效窗口最大值 `<250 ms` | Agent/日志不得长时间占住 GUI |

100 ms 来自现有健康同区域输入回归目标；当前没有依据改成 150 ms。15 FPS 是依据
近期健康本机动态窗口约 19–24 FPS 设置的 v1 可用性下限，同时保留 90% 配对要求。
这些门槛只对本节固定环境和负载生效。

### 4.2 驱动指标与体验护栏

| 指标 | 门槛 |
| --- | --- |
| runtime ACK → GUI 消费 | batch、empty sync、state sync 分组；所有已发送样本完整，窗口最大值 `<250 ms` |
| terminal 可见延迟 | runtime 消费 terminal 至对应 Agent 终态完成绘制，每端最大值 `≤500 ms` |
| 启动可交互 | 五次冷启动，进程创建至首个可交互 GUI 最大值 `≤5 s`；事件循环入口至首次派发和首次心跳分别 `<250 ms` |
| 首帧推进 | 必需通道全部打开后，首次成功新帧呈现 `<10 s` |
| 输入完整性 | 零缺失、零重复、零错误目标、零失焦后继续发送；输入控制丢失立即失败 |
| Agent 完整性 | 两端最终字节数和 SHA256 与 fixture 一致，`output_gap=false`，任务只完成一次 |
| 诊断完整性 | trace/诊断 FIFO 零溢出、零丢失、状态提交成功；证据版本完成后才允许退出 |
| 流与通道 | media/control/Agent 三通道在窗口内持续工作，队列有界，租约有效 |
| 解码/呈现 | 启动和稳定期 decode/present failure 均为 0；两帧上限和 latest-frame 语义保持 |

输入 P99、最大值、各阶段 P50/P95/P99/max、进程 CPU、工作集、GPU 引擎利用率和
队列峰值在 v1 必须报告，但暂不新增硬阈值。取得至少五个完整 `PB-REL-1` 运行后，
才能基于分布补资源门槛；单次历史值不能直接成为支持配置承诺。

## 5. 默认配置与原生尺寸

- **产品主门禁**使用默认窗口适配策略。Controller 播放内容区固定为 1280×720，
  编码可见区域不得低于 1280×720；不能通过缩小窗口或降低画质通过。
- **原生能力门禁**使用 `--stream-qa-native-size` 单独执行一轮完整 30/30/30 窗口。
  它必须通过全部正确性、心跳、ACK、terminal 和绝对 15 FPS 门槛，并证明采集、编码
  可见区域、解码内容均为 1920×1080，纹理仅允许对齐增大。CPU transfer、software
  frame 和 surface fallback 必须为 0。
- 原生 QA 参数不写用户设置。原生能力轮不替代默认产品三轮；其相对 FPS 继续报告，
  v1 不把 QA-only 原生模式的 90% 比值当作产品发布门槛。

## 6. 聚合和证据规则

- P95/P99 使用原始样本 nearest-rank 计算。输入按独立序列批次计算，down/up 事件数
  另报；不把相关事件当成双倍独立样本。
- 输入按发送时刻归属，并保留窗口结束后到达的收据/ACK；耗时样本按完成时刻归属，
  跨边界数量单列。窗口统计和会话累计最大值分开。
- 三轮中的任一有效窗口或任一 KPI 失败，配置即失败。增加轮次不能稀释已有失败。
- 只有可证明的外部焦点、几何、场景或容量干扰可标 invalid；保留原始证据并重跑整轮。
- 结果只有 `passed`、`failed`、`invalid`、`unverified`。缺少 Release-QA、硬件身份、
  样本、窗口或证据时使用 `unverified`，不能解释为通过。
- 证据包必须包含：源码提交/dirty 清单、Release-QA 与产品 Release SHA256、编译差异、
  OS/CPU/GPU/驱动/内存/电源/显示器、场景报告、窗口边界、输入收据、ACK 分类、双端
  trace、日志、任务文本 SHA256、播放截图、进程退出码和孤儿进程检查。
- 正式采集关闭 D3D11 debug layer；诊断运行单独保存。详细事件只在 QA 窗口启用，
  不逐事件同步落盘。

## 7. `DBG-X1` 的新角色

现有 Debug fixture 保持双向各 128×8192 字节、无节奏、1 MiB 长行。它继续要求：

- 文本完整、三通道/租约有效、队列有界、零诊断丢失；
- 零解码/呈现失败，原生路径不得 CPU 回退；
- 输入、ACK、心跳、相对/绝对 FPS 和所有阶段分布完整报告。

其性能失败保留为研发问题并用于 A/B，不再单独把产品状态判为 failed，也不阻塞功能
开发。正确性失败仍然阻断；相对已保存基线出现的新秒级停顿进入高优先级性能待办，
在发布候选阶段结合 `PB-REL-1` 决策。具体基线数值只记录在本地证据中。

## 8. 实施与关闭条件

功能开发已经可以继续，发布资格仍需在发布候选阶段依次完成：

1. `P1-AG-01R-UNBLOCK1`：移除严格性能数值对功能开发的阻塞，只保留正确性硬门禁，
   **已完成并通过**。
2. `P1-AG-01R-PB1`：增加最小 `Release-QA` 构建入口、`AGENT-PACED-1` 生成器及
   v1 评估器；先用合同测试证明窗口、批次、阈值等号和 invalid 规则。
3. `P1-AG-01R-PB2`：在合格参考机运行默认三轮、原生能力一轮、五次冷启动和 UI
   覆盖，导出完整证据。通过后产品本地性能才可记为 passed。
4. `P1-AG-01R-PB3`：使用正式 Release 与真实 Provider 做物理双机确认。因真实输出
   不确定，只与 `AGENT-PACED-1` 对照并报告，不修改已完成基线。

PB1 不再是当前功能开发的前置条件；进入发布候选时再完成。后续不重复现有 Debug
三轮，也不以提高超时、降低分辨率、隐藏面板或丢文本取得通过。异地换向、远端更新
和 GitHub 发布仍由各自门禁管理。

## 9. 依据与置信度

- [原始 KPI 表](test-matrix.md#kpi-baselines-initial)给出健康同区域输入目标 80 ms、
  P95 超过 100 ms 的回归失败线。
- 已完成的门禁审查确认运行心跳、ACK、FPS、原生路径和正确性指标适合持续观测，
  同时确认 Debug 无节奏长行不能直接作为产品负载或功能发布阻塞条件。
- 历史 Debug 运行同时包含健康窗口和有效性能失败；原始数值与产物身份保存在本地
  证据中，用于后续同口径 A/B，不写入公开源码历史。
- 目标、统计口径和正确性门禁置信度为高；`AGENT-PACED-1` 节奏、15 FPS 绝对下限
  和资源指标的置信度为中等。真实 Provider 数据积累后按版本审查，不能回写历史结果。
